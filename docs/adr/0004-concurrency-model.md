## Context

KB-AI 当前所有外部 I/O 是**同步 urllib**(`backend/core/rag/llm.py`、`embedder.py`、`qdrant_store.py`、`query_rewriter.py`、`mineru.py`),FastAPI 的 SSE 端点用「`run_in_executor` 线程 worker + `asyncio.Queue` 桥接」模式(`backend/api/chat.py:366-386`、`backend/api/agent.py:108-133`、`boot.py:259-270`)。REVIEW-GUIDE 自认两条短板:

1. **SSE 断连后 worker 不可取消**(`docs/REVIEW-GUIDE.md:31`):客户端断开时 `sse_starlette` 取消的是 async 生成器,线程 worker 会继续跑完当前 LLM 调用。
2. **Agent 步骤间无并发**(`docs/REVIEW-GUIDE.md:33`):`run_agent` 是串行生成器,单步只调一个工具。

本 ADR 评估:这个模型在什么场景下"够用",什么条件下必须改,以及改的优先级排序。

## 现状量化(单用户 QPS 假设)

| 量 | 值 | 来源 |
|---|---|---|
| 用户数 | 1(单机 U 盘部署,start.bat 双击) | 产品定位(AGENTS.md §0) |
| 并发聊天 | ≤2 个窗口同时开(人工操作上限) | 单用户行为假设 |
| 单轮 RAG /api/chat p95 | ~4-10s | v2.1.0 评测 p50 12.4s(p95 60.3s 含多步 Agent) |
| Agent 多步 p95 | ~60s(max_steps 8 内) | `docs/eval/2026-08-28-golden-agent-v210-report.md` |
| 有效 QPS | ≈ 0.02-0.2(一次请求持续秒级) | 上述延迟反推 |
| 线程池 | `run_in_executor(None, ...)` 默认池 = `min(32, cpu+4)` | CPython asyncio 默认 |
| 峰值并发线程 | 2 请求 × 每请求 1 worker = 2 线程 | 远低于池上限 |

结论:峰值并发 2 个 worker 线程,池上限 32+,**当前模型下并发资源远未成为瓶颈**。真正的瓶颈是单次 LLM 调用延迟(秒级~分钟级),这是产品体验问题不是并发问题。

## 选项对比

| # | 选项 | 收益 | 成本/风险 | 单用户价值 |
|---|---|---|---|---|
| A | **httpx async 化**(llm/embedder/qdrant/rewriter 全量异步化 + 共享 client) | 并发复用连接池;真正可取消;事件循环内单线程高吞吐 | 触碰全部 RAG 模块 + 全部单测重写(mock 层/SSE 桥接层全换);风险撞锁版 `/api/chat` 契约;回归面巨大 | 🟢 低 —— QPS 0.2 用不上吞吐,取消收益可用更廉价手段获得 |
| B | **SSE 断连取消传播**(worker 加 stop 标志/Event,断连置位,worker 在步骤间检查退出;in-flight urllib 调用不可中断,等它自然结束) | 断连后不再跑后续步骤,省 token;实现 ~30-60 行 | 只能"步骤间取消",不能打断进行中的单次 LLM 调用(urllib 无 socket 级取消);需测断连→worker 退出的时序 | 🟡 中 —— 省 token 有真实价值(Agent 多步放大),是"便宜的先做"项 |
| C | **工具级并发**(Agent 单步内多个相互独立的工具并行执行) | 缩短多工具任务延迟(kb_search+calculator 场景可省 1 轮 RTT) | 改变 Agent 语义(tool_call 是批量的,而当前 loop 按单工具迭代);OpenAI 协议原生支持批量 tool_calls,但本实现要重构 loop 状态机;评测 23 条要回归 | 🟢 低 —— 当前数据集里多工具任务少,p95 主要被 LLM 思考时间主导,并行收益 <10% |
| D | **任务队列 + 限流**(请求入队、worker 池消费、满则 429) | 并发可控、背压语义、为 SaaS 化铺路 | 单用户场景纯负债(复杂度>收益);429 在单用户产品里几乎不会触发 | 🟢 低 —— 留给 SaaS 化(见下) |

## Decision

**保持现状:同步 urllib + `run_in_executor` 线程池桥接,不在 v2.2 做并发改造。** 理由按权重排序:

1. **量化后无瓶颈**:峰值 2 worker vs 池上限 32,并发资源富余一个数量级;用户可感知的延迟瓶颈是 LLM 单次调用本身,换并发模型不改变这个上限(同一模型同一请求,async 与 sync 的墙钟时间相同)。
2. **回归风险 vs 收益严重失衡**:A 选项要重写 5 个 RAG 模块 + SSE 桥接 + 全部相关单测,而收益在 QPS 0.2 的场景下不可观测;项目已有多轮"锁版契约"教训(`/api/chat` 契约、镜像 tag),为假设的并发需求动全链路不划算。
3. **真正的可执行改进已识别**:B(断连取消)是唯一有真实收益且低风险的项目 —— Agent 断连后每省一步 = 省一次 LLM 调用(5,478 tokens/任务量级)。它不需要动 I/O 层,只需在 `_worker` 与 `run_agent` 之间传一个取消标志。**记 v2.2 之后候选,不占本期窗口。**
4. **采样证据支持":实测评测 23 条全链路(含 5 个并发请求的评测脚本场景)零中断**(v2.1.0 报告"流式链路零回归")—— 现有桥接在真实负载下被验证过。

## 什么条件下必须改(SaaS 化触发线)

| 触发条件 | 届时方案 | 与 FAQ#10 的呼应 |
|---|---|---|
| 并发 > ~4-8 同时请求 | 选项 A:httpx async 化 + 共享 client(连接池复用),按模块渐进替换,不以"大爆炸"方式重写 | FAQ#10「架构:U 盘单机 → 云部署,容器化已就绪」 |
| 需要租户级配额/限流 | 选项 D:滑动窗口限流中间件 + 429 契约(现成本阻断可映射为租户用量) | FAQ#10「配额:现成本阻断天然可映射成租户级用量计费」 |
| 多工具 Agent 成为主流 | 选项 C:OpenAI 批量 tool_calls + loop 状态机改造 | 池外清单「多 Agent 编排」明确不做,但批量工具调用是单 Agent 内并行,届时重新评估 |
| 断连浪费可量化(多用户 × 多步) | 选项 B:取消传播(优先于 A,C 实施) | 与「评测/成本可见」叙事一致:先度量再改 |

演进顺序建议:**B → A → D → C**(先廉价止损,再架构级改造,限流随 SaaS 化,工具级并发最后,因为它改动语义最重而收益最低)。

## 代价与缓解

| 代价 | 缓解 |
|---|---|
| 断连后当前 LLM 调用仍会跑完(最多浪费 1 次调用) | max_steps 硬顶 + 单次调用延迟有限;选项 B 落地后步骤间可中断,浪费上限收敛为 1 次 |
| 线程池模式不是"最现代"的异步写法,面试可能被质疑 | 本 ADR 就是口径:量化 → 选项对比 → 明确触发线;「知道 httpx async 化怎么做、为什么现在不做」比「为了写法好看而重写」更有说服力 |
| 评测脚本以并发方式跑 23 条(23 个请求近似同时)未触发问题 | v2.1.0/v2.2 评测报告是现成证据 |

## Open Questions(不阻塞)

1. 选项 B(断连取消)是否在 v2.2 后立即实施?→ 倾向是,它是 4 个选项里唯一"低成本 + 可量化收益(token 节省)"的。
2. 若未来出现「同一用户开 5+ 窗口」的实测场景,先量化再决定是否提前走选项 A。
