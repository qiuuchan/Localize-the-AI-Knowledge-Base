# v1.2 RAG 质量提升设计

> 日期：2026-07-21  
> 状态：规格自审通过，待用户审阅  
> 范围：KB-AI v1.2，四类已知 RAG 质量短板全部收口

## 1. 背景与问题证据

v1.1.0 已完成并验证。当前已知的 RAG 质量短板记录在 `docs/known-limitations.md:65-74`：

1. xlsx“名单/进度表”类文档召回弱，现状原因是 Excel 切分粒度粗、行级数据表达不足；
2. 极短问题（少于 4 字）因 hybrid keyword 召回过多而噪声偏高；
3. 长问题（超过 200 字）首字时间约 3-5 秒，现有原因分析指向 embedding/reranker 的长输入成本；
4. 同一文档同时包含“财务预算 2025”和“财务预算 2026”时，当前 temporal weighting 未对明确年份做强约束。

当前 xlsx 解析器在 `backend/core/rag/mineru.py:104-117` 将工作表直接转成 Markdown 表格；当前表格 chunker 在 `backend/core/rag/chunker.py:254-286` 会保留表头并按字符长度分组，但没有行级业务字段元数据。当前关键词索引在 `backend/core/rag/keyword_index.py:101-135` 按命中 token 数排序；当前融合、rerank、时间权重顺序在 `backend/core/rag/retriever.py:301-372`。

现有黄金集工具只检查期望 source 和关键词（`tests/eval/run_eval.py:54-81`），因此本阶段需要扩展评测资产和 diagnostics，才能证明四类问题确实改善。

## 2. 用户目标与范围

### 2.1 用户目标

面向餐饮分公司总经理的日常知识库问答，v1.2 要让以下问题更稳定：

- 查询名单、进度表、预算表时，能按工作表、列名和值召回对应记录；
- 输入极短业务词时，减少单字关键词造成的无关结果；
- 粘贴较长背景描述后，检索阶段首字等待时间可控；
- 明确询问某个年份时，优先回答该年份，而不是被同文档其他年份覆盖。

### 2.2 本阶段范围

- xlsx 结构化行文本和表格元数据；
- chunk 的年份提取和 payload 传递；
- query profile（长度、token、显式年份）；
- 极短问题的精度门控；
- 长问题的 reranker 查询压缩和候选数自适应；
- 显式年份优先排序与兼容回退；
- 40 条以上黄金问答集及检索阶段耗时统计；
- 一次显式旧文档 reparse/reingest 任务。

### 2.3 非目标

- 不替换 `text-embedding-v3`、Qdrant 或现有 cross-encoder；
- 不引入 SQLite FTS5/BM25 或新的第三方依赖；
- 不改变聊天 SSE、citations 字段和前端交互契约；
- 不把 LLM 最终答案正确性作为自动硬门槛，本阶段只自动验收检索层；
- 不在启动时自动全量重入库；
- 不处理视频、多用户隔离、移动端、主动推送等产品能力。

## 3. 总体架构

### 3.1 入库流

```text
xlsx/文档
  -> 文件类型解析
  -> xlsx 行记录结构化（普通文档保持原逻辑）
  -> chunk + table/year metadata
  -> text-embedding-v3
  -> Qdrant payload + SQLite keyword_index
```

### 3.2 查询流

```text
用户问题
  -> query_profile（本地、确定性、无网络）
  -> 现有 entity link / query rewrite
  -> vector recall + keyword recall
  -> RRF
  -> 短问题门控 / 年份优先
  -> 长问题 rerank query 压缩 + 自适应候选数
  -> 现有 rerank / temporal weight / fallback
  -> citations 与聊天 SSE
```

普通聊天路径的返回结构不变；新增的画像、年份命中和阶段耗时主要出现在 `/api/debug/retrieval` 与评测结果中。

## 4. 详细设计

### 4.1 xlsx 结构化表示

`_read_xlsx` 保持 openpyxl、`data_only=True`、只读模式和现有文件类型分发，但输出从宽 Markdown 表改为“工作表 + 表头 + 记录”的检索友好文本。例如：

```text
# 工作表：门店进度
表头：姓名 | 门店 | 进度 | 日期
第 2 行：姓名=张三；门店=一店；进度=完成；日期=2026-06-30
第 3 行：姓名=李四；门店=二店；进度=待确认；日期=2026-07-01
```

规则：

- 每个工作表独立处理；第一个有效行作为表头；没有可靠表头时使用 `列 A`、`列 B` 等位置名；
- 空行跳过，空单元格不输出 `None` 等无意义文本；
- 每条记录保持完整，不允许从一条记录中间切开；连续记录可合并到当前 `max_len=800` 上限内；
- 每个合并块重复工作表名和表头；
- 空表或只有表头的工作表不生成空 chunk；
- 继续使用既有 openpyxl 可选依赖；依赖不可用时沿用现有明确失败行为，不静默降级成纯文本。

xlsx chunk 增加以下元数据：

```json
{
  "chunk_type": "xlsx_row_group",
  "sheet_name": "门店进度",
  "row_start": 2,
  "row_end": 3,
  "columns": ["姓名", "门店", "进度", "日期"],
  "year_mentions": [2026]
}
```

字段名可以在实现时保持 Python 项目现有 snake_case 约定。旧普通文档的 `chunk_type="text"` 行为不变。

### 4.2 年份元数据

新增纯函数从 chunk 文本和文档日期中提取显式四位年份：

- 支持 `20xx`，并避免从更长数字中误截取；
- 支持一个 chunk 或问题包含多个年份；
- 本阶段不扩展中文数字（如“二〇二五”）和复杂相对时间；
- 提取失败只产生空列表，不阻断入库；
- 旧 Qdrant payload 缺少 `year_mentions` 时按空列表兼容处理。

### 4.3 query profile

新增 `backend/core/rag/query_profile.py`，只做确定性本地处理，输出：

```text
char_count              # 去空白后的字符数
meaningful_token_count  # tokenizer 去停用词后的 token 数
explicit_years          # 排序后的四位年份列表
is_short                # char_count <= 4 或有效 token <= 2
is_long                 # char_count > 200
```

该模块还提供 reranker 查询压缩：embedding 和 keyword leg 仍使用完整问题，只有 cross-encoder 使用压缩后的 query。压缩必须保留显式年份，并保留问题开头和结尾的关键信息；不能把完整原问题从评测和 diagnostics 中泄露到日志之外。

### 4.4 极短问题策略

普通问题保持现有 vector + keyword + RRF 流程。`is_short` 为真时：

- 单一泛化 token 的 keyword 命中不能单独决定结果；
- 多 token 查询要求至少两个不同 token 重合，或候选文本包含完整短语；
- 继续保留 vector leg，避免合法专有名词被关键词规则误删；
- 严格规则造成空结果时，自动回退到当前宽松策略，并在 diagnostics 标记 `short_query_fallback`；
- 不修改 keyword_index 的持久化 schema。

### 4.5 明确年份策略

年份策略在候选召回后、最终排序前执行：

- 若 query profile 含一个或多个年份，且候选中存在对应年份 chunk，则稳定地把年份命中候选排在非命中候选之前；
- 问题含多个年份时，命中任意一个明确年份即视为年份命中；
- 候选中没有任何年份命中时不硬过滤，不把结果清空，并记录 `year_match_miss`；
- 年份分组内部继续使用现有 rerank 和 temporal weight；年份优先级高于通用的新旧时间衰减；
- 最终结果保留 `year_match` 和 `year_mentions` 供 debug 与评测使用，不改变 citations 外部契约。

### 4.6 长问题性能策略

对 `char_count > 200` 的问题：

- embedding 仍接收完整原问题，避免召回语义丢失；
- reranker 接收压缩 query，并保留年份和首尾关键信息；
- 默认 rerank 候选数从当前 10 降到 5；低置信度时复用现有 fallback 机制扩大召回；
- 记录 `retrieve_ms`、`embed_ms`、`rerank_ms`、`query_profile` 和实际候选数；
- reranker 不可用时沿用当前原顺序降级，不因性能策略抛错。

阶段耗时不得记录 API key、绝对路径或完整外部错误响应。

## 5. 显式 reparse/reingest

### 5.1 不能复用现有 reembed

现有 `POST /knowledge/documents/{source}/reembed` 的语义是“不重新解析，只重新嵌入已有 chunk”，其流程明确记录在 `backend/api/knowledge.py:595-609`。因此它不能让已有 xlsx 使用新的行结构。

### 5.2 新任务语义

固定实现为新增本地接口 `POST /api/knowledge/documents/{source}/reparse`，不复用现有 `reembed` 路由。接口只接受以下 query 参数：

- `database_id`：目标知识库，默认 `default`；
- `upload_path`：相对于 `data/uploads` 的原文件路径。

服务端必须对 `upload_path` 做 `resolve()`，确认目标是普通文件且仍位于 `_UPLOAD_DIR` 内，拒绝绝对路径和路径穿越；`source` 仍由调用方显式提供，不从用户路径推导。配套新增 PowerShell 5.1 兼容的一次性 `scripts/reparse-rag.ps1`，负责传入文件清单、调用本地接口并轮询现有 task 状态。该脚本不自动运行。

任务操作类型记为 `reparse`，输入为 `database_id`、`source` 和经过路径校验的原文件相对路径。

任务重复使用现有完整入库链路：

```text
原文件
  -> parse_to_markdown
  -> xlsx structure
  -> chunk
  -> embed
  -> staged validation
  -> replace Qdrant points
  -> rebuild keyword_index
```

实现约束：

- 不自动在启动阶段运行；
- 解析、切片、embedding 和向量维度校验全部成功后才进入替换阶段；
- 替换前保留旧 source，前置阶段失败时旧索引不动；
- 成功替换后清理旧 point IDs，并以新 chunks 完整重建该 source 的 keyword_index；
- Qdrant 清理、写入或 SQLite 重建任一步失败，任务标记失败并记录 degradation，不报告成功；
- 任务状态写入现有 `processing_state`，可通过现有 task 查询方式轮询；
- `reembed` 端点保持原有语义，不通过模糊参数改变其行为；
- 迁移前应使用现有本地备份流程，迁移报告必须列出成功、失败、chunk 数和 warning。

该任务不改变普通上传的前端契约；前端不增加自动迁移入口，迁移只通过 `scripts/reparse-rag.ps1` 显式触发。

## 6. 模块与接口边界

| 模块 | 职责 | 保持不变的边界 |
|---|---|---|
| `backend/core/rag/mineru.py` | xlsx 文件读取与结构化文本生成 | `parse_to_markdown` 返回 `{markdown, method, cache_hit}` |
| `backend/core/rag/query_profile.py` | query profile、年份提取、rerank query 压缩 | 纯 Python、无网络 |
| `backend/core/rag/chunker.py` | chunk 边界与 metadata 传递 | 普通 Markdown/TXT chunk 行为 |
| `backend/core/rag/retriever.py` | 画像策略、融合、年份排序、fallback | `retrieve()` 主调用方式 |
| `backend/core/rag/reranker.py` | cross-encoder 评分与降级 | `rerank(query, candidates, top_k, model_name)` |
| `backend/core/rag/qdrant_store.py` | reparse 后按 point IDs 清理旧点 | collection、向量维度和搜索 contract |
| `backend/core/rag/keyword_index.py` | 对目标 source 重建关键词行 | 现有表 schema |
| `backend/api/knowledge.py` | 新增本地 reparse task 路由 | 普通 upload/reembed 语义 |
| `backend/api/debug.py` | 暴露检索诊断 | 原有字段继续存在 |
| `scripts/reparse-rag.ps1` | 显式调用 reparse 并轮询任务 | PowerShell 5.1、不会自动运行 |
| `tests/eval/run_eval.py` | 黄金集执行、分类统计、耗时统计 | 退出码语义保持 0/1/2 |

Qdrant payload 允许增加字段，不改变 collection 名、向量维度或距离；SQLite keyword_index 不新增第三方索引依赖。

## 7. 错误处理与兼容

- openpyxl 缺失：任务失败并返回现有可诊断错误；不把 xlsx 当 TXT；
- xlsx 表结构异常：跳过不可用行并记录 warning；如果最终没有有效记录，任务失败；
- 年份元数据异常：使用空元数据继续入库；
- 严格短问题没有结果：回退宽松策略，不把检索失败伪装成“知识库没有资料”；
- 明确年份无候选命中：保留结果并标记 `year_match_miss`；
- reranker 未安装、模型未缓存或推理异常：沿用当前降级路径；
- reparse 前置处理失败：旧 Qdrant/keyword index 保持不动；替换阶段部分失败：任务失败、写 degradation、提供可重复重跑状态；
- 所有新日志和 diagnostics 继续遵守现有敏感信息脱敏约束。

## 8. 测试与评测

### 8.1 单元测试

新增或扩展 `tests/unit/`：

- xlsx 表头、工作表、空单元格、记录边界和 chunk_type；
- 四位年份提取、多个年份、无年份和数字误匹配；
- query profile 的短/普通/长边界；
- rerank query 压缩保留首尾和年份；
- 短问题 token 重合门控、完整短语和宽松 fallback；
- 年份命中排序、无命中回退、多个年份；
- reparse 成功、前置失败保留旧索引、Qdrant/keyword index 一致性；
- 旧 payload 缺少新字段时的兼容路径。

### 8.2 黄金问答集

沿用 `tests/eval/run_eval.py` 的 JSONL 形式，扩展可选字段：

```json
{
  "question": "2026 年门店进度如何？",
  "expect_source": "progress.xlsx",
  "expect_keywords": ["完成"],
  "category": "year",
  "expect_year": 2026,
  "expect_chunk_type": "xlsx_row_group"
}
```

要求：

- 至少 40 条；xlsx、极短、长问题、年份四类各至少 10 条；
- source、keyword 仍为基础通过条件；
- `expect_year` 和 `expect_chunk_type` 只在相关类别使用；
- 原有基线用例保持可运行；
- 评测报告按 category 输出通过数、失败原因和耗时，但整体通过率是本阶段硬门槛。

### 8.3 性能测量

- 评测开始先执行一次 warm-up，避免把首次模型加载当作业务请求；
- 对 `category=long` 的用例记录检索总耗时及 `embed_ms`/`rerank_ms`；
- 以长问题样本的 p95 作为门槛，目标为检索阶段 `p95 <= 3s`；
- 如果样本量不足以计算稳定 p95，报告实际样本数，不将不足样本伪装成通过；
- 性能优化不得牺牲四类黄金集整体通过率或既有基线。

## 9. 交付顺序

### PR1：评测与 query profile 基础

先增加 query profile、diagnostics、评测分类和耗时字段，确认现有行为基线不回归。

### PR2：xlsx 结构化与年份元数据

实现 xlsx 行记录、Chunk/payload 字段和显式 reparse 任务，完成结构化入库与迁移测试。

### PR3：短问题与年份排序

接入短问题精度门控、年份优先排序、无命中兼容回退，完成检索行为测试。

### PR4：长问题性能优化

接入 reranker query 压缩、长问题候选数自适应和 p95 评测，完成发布前全量验证。

## 10. 验收标准

1. 黄金集不少于 40 条，四类各不少于 10 条；
2. 检索层整体通过率达到至少 90%；
3. 既有单元测试、API 集成测试和已有黄金用例零回归；
4. 长问题检索阶段 p95 不超过 3 秒，且报告真实样本数；
5. xlsx 能通过工作表、列名和值召回对应 row group；
6. 明确年份且存在对应候选时，第一屏结果优先命中该年份；无对应候选时不清空结果；
7. reparse 成功后 Qdrant 与 keyword_index 对目标 source 的 chunk 集合一致；
8. reparse 前置失败不破坏旧索引，失败任务可诊断并可重跑；
9. 不增加第三方依赖、不改变 Embedding/Qdrant contract、不改变聊天 SSE 和前端契约；
10. `scripts/run-checks.ps1` 全部通过，且新增测试有明确覆盖。

## 11. 明确推迟项

以下不纳入 v1.2 设计：

- SQLite FTS5/BM25 全量替换当前 keyword_index；
- 中文数字年份和复杂相对时间理解；
- LLM 最终答案自动评分；
- 真实外部 API 成本预算与月度账单告警；
- xlsx 之外的 PDF 表格 OCR 质量专项；
- 视频、多用户、移动端和主动推送。
