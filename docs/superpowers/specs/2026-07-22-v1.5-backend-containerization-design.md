## 2. 文件级变更详情

### 2.1 Item 1 · backend 多阶段 Dockerfile

**新建** `E:/docker/backend/Dockerfile`(范式样本,沿用 v1.4.0 §2.2 路径):

```dockerfile
# KB-AI v1.5.0 · 后端多阶段构建范式
# 目的:把 FastAPI backend 从 host 进程迁入 docker compose,与 qdrant / dify-api 等同编排
# 基础镜像:python:3.12-slim(与 .python-version 锁定的 3.12.6 兼容)
# 范式来源:v1.4.0 spec §2.2 伪代码示例
# 边界:不解决 Dify 1.5GB / 冷启动 5-10min(上游问题)

# === Stage 1: builder ===
# 把 backend/requirements.txt 装成 wheels,验证 pip cache + layer 复用
FROM python:3.12-slim AS builder
WORKDIR /build
COPY backend/requirements.txt backend/requirements.txt
RUN pip wheel --wheel-dir=/wheels -r backend/requirements.txt

# === Stage 2: runtime ===
# 从 wheels 离线安装 + 拷贝 backend 源码,最终镜像仅含运行所需
FROM python:3.12-slim
WORKDIR /app

# 系统依赖(curl 给 healthcheck;sqlite3 给 ps/sqlite 子进程兼容)
RUN apt-get update && \
    apt-get install -y --no-install-recommends curl sqlite3 && \
    rm -rf /var/lib/apt/lists/*

# 离线装依赖(从 builder stage 拉 wheels,不联网)
COPY --from=builder /wheels /wheels
COPY backend/requirements.txt /app/backend/requirements.txt
RUN pip install --no-index --find-links=/wheels -r /app/backend/requirements.txt && \
    rm -rf /wheels

# 拷贝 backend 源码
COPY backend/ /app/backend/

# 健康检查端点(/api/health)
HEALTHCHECK --interval=30s --timeout=5s --retries=3 --start-period=20s \
    CMD curl -fsS http://localhost:8000/api/health || exit 1

# 启动 uvicorn:监听 0.0.0.0:8000(由 compose 端口映射到 127.0.0.1:8000)
# --app-dir /app 让 backend 包导入解析为 /app/backend/main.py
CMD ["uvicorn", "backend.main:app", "--host", "0.0.0.0", "--port", "8000", "--app-dir", "/app"]
```

**关键决策**:

- **`python:3.12-slim` 选型**:与 `.python-version` 3.12.6 对齐;`slim` 变体省去编译工具,~120MB base
- **builder 装 wheels → runtime 离线安装**:layer cache 友好,requirements.txt 不变时 wheels 层命中
- **镜像体积预算**:
  - python:3.12-slim ≈ 120MB
  - 7 deps(fastapi / uvicorn / sse-starlette / pydantic / python-multipart / sentence-transformers)≈ 200-250MB
  - backend 源码 ≈ 5MB
  - system deps(curl + sqlite3)≈ 10MB
  - **总计 ≤ 400MB**(目标 ≤ 350MB)
- **`HEALTHCHECK` 内置**:compose 可通过 `condition: service_healthy` 依赖此 backend(未来扩展)
- **`--app-dir /app`**:确保 backend 包路径解析正确

### 2.2 Item 2 · docker-compose 集成 `kb-ai-backend`

**修改** `E:/docker-compose.yml`,在现有 4 个 service 之后新增 `kb-ai-backend` service:

```yaml
  # -----------------------------------------------------------------
  # 5. KB-AI 后端 (FastAPI, v1.5.0 容器化)
  #    把 v0.8.0+ 的 host python 进程迁入 docker,与 qdrant/dify-api 同一编排
  # -----------------------------------------------------------------
  kb-ai-backend:
    # v1.5.0:从 host python 切到 build: (多阶段范式样本,见 docker/backend/Dockerfile)
    build:
      context: .
      dockerfile: docker/backend/Dockerfile
    image: kb-ai/backend:local   # 自定义 tag,避免与 python:3.12-slim 冲突
    container_name: kb-ai-backend
    restart: unless-stopped
    ports:
      - "127.0.0.1:8000:8000"     # FastAPI HTTP (loopback only)
    volumes:
      # 运行时数据卷:与 v0.7.1 一致,以相对路径挂载回 U 盘根
      - ./data:/data
      - ./vectors:/vectors
      - ./cache:/cache
      - ./logs:/logs
      - ./tmp:/tmp
      # frontend dist:由 backend 容器内挂载并由 FastAPI 服务(替代 host 静态挂载)
      - ./frontend/dist:/app/frontend/dist:ro
    environment:
      # ----- 阿里云百炼 API -----
      ALIYUN_BAILIAN_API_KEY: ${ALIYUN_BAILIAN_API_KEY}
      # ----- Websearch 降级(可选) -----
      TAVILY_API_KEY: ${TAVILY_API_KEY:-}
      BING_SEARCH_API_KEY: ${BING_SEARCH_API_KEY:-}
      # ----- 项目根(容器内 /data 等) -----
      KB_AI_ROOT: /data
      # ----- 部署模式 -----
      DEPLOY_ENV: production
      LOG_LEVEL: INFO
    healthcheck:
      # Dockerfile 内已声明 HEALTHCHECK,此处可省略;若省略则用 compose 默认
      # (DOCKERFILE healthcheck 默认会被 compose 复用,但显式声明更清晰)
      test: ["CMD", "curl", "-fsS", "http://localhost:8000/api/health"]
      interval: 30s
      timeout: 5s
      retries: 3
      start_period: 20s
    # 资源限制(参考 qdrant/dify-api 量级,FastAPI 单进程 + 模型加载)
    mem_limit: 1g
    mem_reservation: 512m
    cpus: "1.0"
    pids_limit: 200
    networks:
      - kb-ai-net
    depends_on:
      qdrant:
        condition: service_healthy
      dify-api:
        condition: service_healthy
```

**关键决策**:

- **`build: context: .`(项目根)**:Dockerfile 引用 `backend/requirements.txt` 用相对路径
- **新增 `image: kb-ai/backend:local`**:类比 v1.4.0 `kb-ai/dify-db-init:local`,不与任何已锁版官方镜像冲突
- **`volumes` 全部回 U 盘根**:与 v0.7.1 风格一致(相对路径挂载),保证 U 盘拔插后数据完整
- **`KB_AI_ROOT=/data`**:`backend/core/config.py:get_root_dir()` 需要识别容器根路径(若当前实现用 `Path(__file__).parent.parent` 取项目根,容器内 `/app/backend/` 的 parent 是 `/app` 而非 `/data`;可能需要 backend 微调或环境变量覆盖)
- **`frontend/dist` 挂载到容器只读**:FastAPI `app.mount("/", StaticFiles(...))` 仍生效
- **依赖链**:依赖 qdrant + dify-api 都 healthy,确保 backend 启动时外部依赖就绪

**注意 ⚠️**:`KB_AI_ROOT` 环境变量是否被 backend 识别需要验证(后端业务代码不在 v1.5.0 改动范围);若 `get_root_dir()` 不支持环境变量覆盖,可能需保留 host 路径逻辑 + 数据卷挂载到容器内对应路径(已通过 volumes 一一对应实现)。这一项在实施 Item 5(集成测试)时验证。

### 2.5 Item 5 · 集成测试 + 体积验证

**新建** `E:/tests/integration/test_backend_container.py`:

```python
"""Tests for v1.5.0 backend containerization.

Verifies:
1. docker-compose config syntax valid
2. kb-ai-backend service declared with build: + image: kb-ai/backend:local
3. kb-ai-backend depends on qdrant + dify-api with service_healthy
4. kb-ai-backend healthcheck defined
5. Image volume budget (size check, requires docker build first)
6. start.bat / stop.bat updated to use docker compose for backend
7. Backend Dockerfile multi-stage structure (builder + runtime)
"""
import re
from pathlib import Path

REPO = Path(__file__).resolve().parent.parent.parent


def test_compose_config_parses():
    """docker-compose.yml is valid YAML."""
    import yaml
    compose = REPO / "docker-compose.yml"
    data = yaml.safe_load(compose.read_text(encoding="utf-8"))
    assert "services" in data
    assert "kb-ai-backend" in data["services"]


def test_kb_ai_backend_service_declared():
    """kb-ai-backend service has build: + image: kb-ai/backend:local."""
    import yaml
    compose = REPO / "docker-compose.yml"
    data = yaml.safe_load(compose.read_text(encoding="utf-8"))
    svc = data["services"]["kb-ai-backend"]
    assert "build" in svc
    assert svc["build"]["dockerfile"] == "docker/backend/Dockerfile"
    assert svc["image"] == "kb-ai/backend:local"


def test_kb_ai_backend_depends_on_healthy():
    """kb-ai-backend depends on qdrant + dify-api with service_healthy."""
    import yaml
    compose = REPO / "docker-compose.yml"
    data = yaml.safe_load(compose.read_text(encoding="utf-8"))
    deps = data["services"]["kb-ai-backend"]["depends_on"]
    assert deps.get("qdrant", {}).get("condition") == "service_healthy"
    assert deps.get("dify-api", {}).get("condition") == "service_healthy"


def test_kb_ai_backend_has_healthcheck():
    """kb-ai-backend has healthcheck pointing at /api/health."""
    import yaml
    compose = REPO / "docker-compose.yml"
    data = yaml.safe_load(compose.read_text(encoding="utf-8"))
    hc = data["services"]["kb-ai-backend"]["healthcheck"]
    assert "/api/health" in " ".join(hc["test"])


def test_backend_dockerfile_is_multi_stage():
    """docker/backend/Dockerfile has builder + runtime stages."""
    df = (REPO / "docker/backend/Dockerfile").read_text(encoding="utf-8")
    assert "AS builder" in df
    assert re.search(r"FROM python:3\.12-slim\b", df)
    # At least 2 FROM statements
    assert len(re.findall(r"^FROM ", df, re.MULTILINE)) >= 2
```

## 3. 数据流与集成

### 3.1 启动序列(v1.5.0)

```
docker compose up -d         (start.bat 第 4 步)
  ├─ qdrant         (image: qdrant:1.7.0, 官方)
  ├─ dify-api       (image: langgenius/dify-api:1.0.0, 官方)
  ├─ dify-worker    (image: langgenius/dify-api:1.0.0, 官方)
  ├─ dify-db-init   (build: ./docker/dify-db-init, v1.4.0+ 本地)
  └─ kb-ai-backend  (build: ./docker/backend, v1.5.0+ 本地) ← NEW
        ├─ depends_on: qdrant (service_healthy)
        └─ depends_on: dify-api (service_healthy)

start.bat 第 6 步(幂等)
  └─ docker compose up -d kb-ai-backend    (no-op 若已 up)

start.bat 第 7 步(等待 API 就绪)
  └─ 探测 http://localhost:8000/api/health(由 compose port 转发)

host 端 start.bat 第 6 步末段(向后兼容)
  └─ 拉起 MinerU python 进程(host, 不在容器化范围)
```

### 3.2 backend 容器内 vs host 进程对比

| 维度 | v1.4.0(host 进程) | v1.5.0(容器) |
|---|---|---|
| 入口 | `scripts/start-backend.ps1` | `docker compose up -d kb-ai-backend` |
| 进程名 | `python.exe -m uvicorn ...` | `kb-ai-backend` (container) |
| 监听 | `127.0.0.1:8000` (host loopback) | `0.0.0.0:8000` (容器内)→ 转发到 `127.0.0.1:8000` |
| 数据卷 | host 直接读 `./data` | 容器内挂载 `./data:/data` |
| 环境变量 | host `.env` | compose env_from `.env` |
| 依赖管理 | host `backend/.venv` | 容器内 `pip install`(wheels) |
| 健康检查 | 无 | `HEALTHCHECK` curl /api/health |

  - **2 个本地构建 tag 保留**:kb-ai/dify-db-init:local(v1.4.0 引入) + kb-ai/backend:local(v1.5.0 新增)
- `docker/backend/Dockerfile` 是新文件,不在 AGENTS.md 红线保护范围

### 4.3 风险与缓解

| 风险 | 等级 | 缓解 |
|---|---|---|
| backend 镜像过大(>500MB) | 🟡 | 多阶段 + slim base + wheels;测试强制 ≤ 400MB;若超则考虑 alpine 变体(后续优化) |
| start.bat 第 6 步 `docker compose up -d kb-ai-backend` 在容器已 up 时无副作用 | 🟢 | compose `up -d` 幂等;已在第 4 步整体 up,此处 no-op |
| stop.bat 第 1 步 `docker compose stop kb-ai-backend` 后,第 2 步 `docker compose stop` 可能重复 stop | 🟢 | compose `stop` 对已停止容器 no-op |
| backend 容器内 `backend/.venv` 不存在 → 启动失败 | 🟢 | Dockerfile 直接 `pip install`,不依赖 .venv |
| `KB_AI_ROOT=/data` 与 backend 业务代码不兼容 | 🟡 | 验证:`backend/core/config.py:get_root_dir()` 是否读环境变量;若不读,volumes 已把 /data 等对应挂载,可能无需环境变量;Item 5 测试验证 |
| 用户误解 v1.5.0 优化了 1.5GB 镜像 | 🟡 | `docs/backend-container.md §1.1` 边界声明开篇明示;`CHANGELOG` v1.5.0 段说明"仅后端容器化,Dify 镜像未变" |
| 用户误解 v1.5.0 把 MinerU 也容器化了 | 🟡 | `docs/backend-container.md §4.3` 明确推迟 MinerU;CHANGELOG §4 同步 |
| start.bat / stop.bat 红线触发 | 🟡 | spec §1.4 已声明需用户授权;参照 v0.8.4 + v0.8.6 先例,授权流程一致 |
| backend `.env` 注入 ALIYUN_BAILIAN_API_KEY 失败 → 启动后调用 API 401 | 🟡 | compose env_from 自动从 `.env` 读;与现有 dify-api 服务一致 |
