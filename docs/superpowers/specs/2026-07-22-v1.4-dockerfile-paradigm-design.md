## 2. 文件级变更详情

### 2.1 Item 1 · dify-db-init 多阶段 Dockerfile 范式

**当前**:`E:/docker-compose.yml:177-208` `dify-db-init` service 直接用 `image: alpine:3.19` + inline `entrypoint:` + inline `command:`(shell 脚本:apk add sqlite + PRAGMA)。

**变更动机**:

- **演示目的**:把多阶段构建范式落地,作为未来 backend / frontend 容器化时可直接复制的模板
- **构建契约**:让 `docker-compose.yml` 拥有可构建产物(`build:` 字段),未来加新 service 时不再 100% 依赖外部镜像
- **功能等价**:`dify-db-init` 实际只需要 alpine + sqlite3,行为不变

**变更**:

1. **新建 `E:/docker/dify-db-init/Dockerfile`**(8 行,纯范式样本):

   ```dockerfile
   # KB-AI v1.4.0 · 多阶段构建范式样本
   # 目的:为未来 backend / frontend 容器化预留可复用的多阶段模板
   # 现状:dify-db-init 仅需 alpine + sqlite,builder 与 runtime 共享 base;多阶段用作范式示例
   # 边界:本镜像实际功能等价于直接使用 alpine:3.19 + apk add sqlite;多阶段语法仅为未来扩展入口

   # === Stage 1: builder ===
   # 在独立阶段装 sqlite,验证 apk cache + layer 复用
   FROM alpine:3.19 AS builder
   RUN apk add --no-cache sqlite

   # === Stage 2: runtime ===
   # COPY builder 产物到最终镜像;若未来需要 init.sql 模板或额外工具,在 builder 阶段注入即可
   FROM alpine:3.19
   COPY --from=builder /usr/bin/sqlite3 /usr/bin/sqlite3
   ```

2. **修改 `E:/docker-compose.yml:177-208` 的 `dify-db-init` service**:

   ```yaml
   dify-db-init:
     # v1.4.0:从 image: alpine:3.19 切到 build: (多阶段范式样本,见 docker/dify-db-init/Dockerfile)
     build:
       context: ./docker/dify-db-init
       dockerfile: Dockerfile
     image: kb-ai/dify-db-init:local   # 自定义 tag,避免与 alpine:3.19 冲突
     container_name: kb-ai-dify-db-init
     restart: "no"
     # ... 其余字段(volumes / networks / depends_on / 资源限制 / entrypoint / command)不变
   ```

   **关键细节**:
   - `image: kb-ai/dify-db-init:local` 是**新引入的本地 tag**,不与任何已锁版的官方镜像冲突(锁版清单只约束 4 个原 service 的 tag;dify-db-init 的 image 字段本身就是新增的)
   - `context: ./docker/dify-db-init` 走相对路径,匹配 compose 现有风格(`./data` / `./vectors` 等)
   - `entrypoint:` 和 `command:` 保留原状,行为完全等价

3. **首次构建性能**(对日常体验影响):

   - `docker compose build dify-db-init` 首次 ~5-8s(拉 alpine:3.19 基础 + apk 装 sqlite + COPY)
   - 后续 build cache 命中 ~0.5s(无 layer 变更)
   - 对 `start.bat` 用户体验:**首次启动多 ~5-8s**,后续无感(因为 `docker compose up` 自动复用 build cache)

## 3. 数据流与集成

### 3.1 启动序列(v1.4.0 标注)

```
docker compose up
  ├─ qdrant         (image: qdrant:1.7.0,官方)
  ├─ dify-api       (image: langgenius/dify-api:1.0.0,官方)
  ├─ dify-worker    (image: langgenius/dify-api:1.0.0,官方)
  └─ dify-db-init   (build: ./docker/dify-db-init ← v1.4.0 新增 build:
                     builder stage: alpine:3.19 + apk add sqlite
                     runtime stage: alpine:3.19 + COPY sqlite3
                     → image: kb-ai/dify-db-init:local)
```

### 3.2 dify-db-init 行为等价性

**v1.3.1**:
```yaml
image: alpine:3.19
entrypoint: ["/bin/sh", "-c"]
command: |
  apk add --no-cache sqlite >/dev/null 2>&1
  DBFILE=/data/db.sqlite
  if [ ! -f "$$DBFILE" ]; then
    sqlite3 "$$DBFILE" 'VACUUM;'
  fi
  MODE=$$(sqlite3 "$$DBFILE" 'PRAGMA journal_mode=WAL;')
  SYNC=$$(sqlite3 "$$DBFILE" 'PRAGMA synchronous=NORMAL;')
  echo "[dify-db-init] journal_mode=$$MODE synchronous=$$SYNC on $$DBFILE"
```

**v1.4.0**(行为等价):
- `entrypoint:` 和 `command:` 保持完全一致(只把 `image:` 换成 `build:`)
- `apk add --no-cache sqlite` 已通过 Dockerfile builder 阶段预装,runtime 镜像中 sqlite3 已存在
- 唯一区别:`apk add` 在 build 时执行一次(固化到 layer),而非运行时每次执行 → 启动略快但功能完全等价

### 3.3 不变量边界

- `docker-compose.yml` 中 4 个 service 的 `image:` / `build:` 字段最终效果:**所有锁版的官方镜像 tag 保持不变**(qdrant:1.7.0 / dify-api:1.0.0 × 2),**仅 dify-db-init 新增本地 tag** `kb-ai/dify-db-init:local`(这是新引入,不与任何已锁版 tag 冲突)
- `docker/dify-db-init/Dockerfile` 是新文件,不在 AGENTS.md 红线保护范围
- `.dockerignore` 是新文件,GitHub / Docker BuildKit 自动识别
- `docs/docker-build.md` 是新文档

### 4.3 风险与缓解

| 风险 | 等级 | 缓解 |
|---|---|---|
| 用户误解 v1.4.0 优化了 1.5GB 镜像 | 🟡 | `docs/docker-build.md` §1.3 边界声明开篇明示;`CHANGELOG.md` v1.4.0 段开篇说明"范式化交付,非性能优化" |
| `docker compose build` 在国内首次慢(alpine:3.19 拉取) | 🟢 | alpine:3.19 仅 5MB,拉取 ~2-3s;远小于 1.5GB Dify 镜像;首启多 ~5-8s 可接受 |
| `.dockerignore` 与未来实际 Dockerfile 不完全匹配 | 🟢 | 范本以"防御性广覆盖"为目标,排除常见污染项;未来具体 Dockerfile 落地时按需微调 |

| `docker compose build` 改动首次触发 `start.bat` 多 ~5-8s | 🟢 | 仅首次,后续 build cache 命中 < 1s;`start.bat` 整体冷启动 60-90s 内仍达标 |
| `docs/docker-build.md` §2.2 扩展路径示例被未来读者误当作"待做清单" | 🟢 | §2.2 明确标注"伪代码,非 v1.4.0 范围";文档末 §4 明确推迟范围 |
| 多阶段 builder stage 在 alpine 共享 layer 时无实际收益 | 🟢 | §2.1 已说明"等价于直接使用 alpine:3.19 + apk add sqlite;多阶段语法仅为未来扩展入口";这是有意为之的范式样本 |

### 4.4 不在 v1.4.0 范围(明确推迟)

- 1.5GB 镜像体积优化(需改 Dify 1.0 源码或换 registry mirror)
- 冷启动 5-10min 加速(需改 Dify 1.0 启动逻辑或配置 registry-mirrors)
- backend / frontend 容器化(见 `docs/docker-build.md §2.2` 扩展路径,等用户决策)
- COS 异地备份(`§4 #5`,用户决策)
- 远程 CI(`§5 #1b`,无 git remote)
- Pester 测试(`§6 #E`,为单一脚本建立框架 ROI 太低,推 v1.4.0+;本版本未触及此 backlog)
- PRD 项目外文件同步(`<private>/.harness/intake/custom-kb-qa-ai-prd-draft.md`,v1.3.0 延期;v1.4.0 不动)
