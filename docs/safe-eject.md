# KB-AI 安全弹出说明(必读!)

> **这是 U 盘方案里最重要的一份文档**  
> 直接拔 U 盘会导致 SQLite 数据库损坏,所有资料可能丢失。  
> 阅读本文约 3 分钟,挽救您可能损失的几个小时数据。

---

## 一句话总结

> **永远先双击 `stop.bat`,等 10 秒,然后再拔 U 盘。**

---

## 为什么不能直接拔?

KB-AI 系统使用 **SQLite** 数据库存储所有元数据(您的文档列表、AI 对话历史、用户配置、向量索引)。

SQLite 的工作模式:

1. 数据先写到内存缓冲区
2. 定期 flush 到磁盘
3. 但**只有执行 `fsync` 系统调用后,数据才真正安全落盘**

直接拔 U 盘会触发两种风险:

### 风险 1:数据库文件半写状态

SQLite 的主数据库文件 `db.sqlite` 是连续写入的。如果正在写入时断电/拔盘,文件可能处于"半写状态"——前面的数据是新的,后面的数据是旧的,中间可能错位。

后果:

- 下次启动 Dify 时,SQLite 检测到损坏,可能自动回滚到某个早期备份点
- **您最近上传的几份文档可能丢失**
- AI 对话历史可能错乱

### 风险 2:WAL 日志未合并

SQLite 默认开 **WAL(Write-Ahead Logging)** 模式。数据先写到 `db.sqlite-wal` 文件,定期合并回主库。

直接拔盘时,WAL 文件可能没合并:

- 主数据库看似完整,但漏掉了 WAL 里的最近数据
- **您最近 1-10 分钟的对话/上传可能丢失**

### 风险 3:U 盘硬件损坏

频繁直接拔盘可能损坏 U 盘的文件系统表(FAT/exFAT),导致整个 U 盘识别不到。

---

## 正确的操作流程

### 步骤 1:先停 Dify 服务

在 U 盘根目录,双击 `stop.bat`。

脚本会做这些事:

```
[1/3] 停止 Docker 容器(给 10 秒优雅退出)
   └─ docker compose down
       └─ 容器收到 SIGTERM → 关闭进程 → SQLite fsync → 数据落盘
[2/3] 等待 SQLite 完成数据落盘
   └─ 5 秒倒计时,确保 WAL 合并
[3/3] 安全弹出 U 盘
   └─ 提示 "现在可以安全弹出 U 盘"
```

### 步骤 2:从系统托盘弹出 USB

1. 看 Windows 任务栏右下角(系统托盘)
2. 找到 "安全删除硬件并弹出媒体" 图标(USB 形状)
3. 点击 → 选择您的 KB-AI U 盘
4. 等待系统提示 "安全地移除设备"
5. 物理拔出 U 盘

**为什么不直接拔了?**  
即使 stop.bat 已经停了容器,操作系统可能还有文件句柄未关闭。从系统托盘弹出是最稳妥的"清场"动作。

---

## 万一忘了一步直接拔了,怎么办?

**不要慌,按顺序尝试**:

### 情况 A:U 盘还能识别

1. 把 U 盘**先不要动**
2. 重新插入(可能已经插着),等待 5 秒
3. 打开 U 盘,看 `data/db.sqlite` 是否还在
4. 双击 `start.bat` 启动系统
5. 进入 Dify,检查文档列表、对话历史是否完整

如果看到 "database disk image is malformed" 之类的错误,说明 SQLite 损坏了:

- 系统可能自动恢复到最近的一致快照
- 您最近几分钟的操作可能丢失
- **建议立刻停止使用,联系工程师**

### 情况 B:U 盘识别不到

1. 换 USB 口试试(优先 USB 3.0 蓝色口)
2. 换电脑试试(Win10/11 都行)
3. 都不行 → U 盘文件系统表损坏,**数据恢复很困难**

**教训**:以后一定要先 stop.bat 再拔!

## 时间分配建议

| 操作 | 何时 | 时间 |
|---|---|---|
| 双击 stop.bat | 决定不用 AI 时 | 10 秒 |
| 等待脚本完成 | stop.bat 运行中 | 15 秒 |
| 系统托盘弹出 USB | 脚本提示后 | 5 秒 |
| 物理拔出 | 系统提示后 | 1 秒 |
| **总计** | | **30 秒** |

30 秒换数据安全,很值。

## 技术原理(给好奇的人)

### SQLite 的 3 个文件

`data/db.sqlite` 目录下有三个关键文件:

```
db.sqlite        ← 主数据库(磁盘上)
db.sqlite-wal    ← 写前日志(WAL 模式,内存→磁盘的中转)
db.sqlite-shm    ← 共享内存索引(多进程读)
```

**正常关闭**:3 个文件状态一致,下次启动无缝衔接。  
**异常断电**:WAL 可能没合并,主库可能半写,SQLite 启动时检测到不匹配,尝试回滚。

### Docker 容器的优雅停止

`docker compose down` 发送 SIGTERM 信号给容器主进程。

Dify 收到信号后:

1. 停止接收新请求
2. 等待正在处理的请求完成(最多 30 秒)
3. 关闭 SQLite 连接(触发 fsync)
4. 关闭网络监听
5. 进程退出

这给了 Dify 充分的时间把内存数据落盘。

如果直接 `kill -9`(相当于拔电),Dify 没机会做这些清理,数据一致性靠 SQLite 自身的恢复机制兜底,但代价是可能丢失最近的数据。
